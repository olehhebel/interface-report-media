The pull request was green. The browser told a different story.

A lighter logo reverted after load. A merged service page stayed unchanged online. Both problems became obvious once we followed the same path as a visitor.

A finished release should survive the first click

A visitor taps a link in a feed. They have no reason to care that your pull request passed every check. They care whether the right page opens and whether the promised action works from the phone in their hand.

Two recent revisions on our own sites made that gap visible. Both were small changes. Either could have been marked complete too early.

The logo that put its weight back on

Interface Report already had a compact copy of its logo, so two article pages could use the 21 KB asset in place of the roughly 846 KB original. The HTML was correct. After load, a shared branding script put the original file back.

The fix was to make the script respect the image already selected by the page. Then we reopened the articles and checked the rendered image. The smaller file is a verified reduction in asset size. A speed claim would require its own measurement.

The merge that never reached the site

The product-design portfolio had a different failure. The new audit page was merged on the default branch. The public site was built from a separate GitHub Pages branch. The old page stayed live until the reviewed changes were released to the actual publishing branch.

After that release, both language versions opened the project brief from the new call to action. Opening the live dialog and testing form handling with a mock response establish two separate facts. Seeing a real submission arrive would establish delivery.

How to collect evidence without guessing

Open a browser at the same URL a customer would use, preferably in a fresh session. Capture the exact URL, the revision GitHub Pages says it deployed, and the visible result. Repeat once from a saved or tagged link if that is how your audience arrives. This helps distinguish a publishing problem from a stale tab or a cached response. A good record is simple enough that someone else can repeat it.

For images, look at the final element and its request in the Network panel. A smaller file in the repository is only the starting point. The browser may fetch an older image from a script, use another file from a responsive source set or request both versions. Record the image URL and transferred size. If you want to evaluate loading speed, run repeatable comparisons and look for field data when your traffic supports it.

For a form, start with the action a customer can perform without submitting anything. Does the right dialog open? Can a person on a phone reach each field and close it? Then test validation and the success and error states with a simulated response. An authorized test against the real system adds a separate piece of evidence: confirmation that the intended inbox or system received the message.

A quick release note should also say what you could not verify. If Google has not crawled the new URL yet, record that state. If you tested only the English route, list the Ukrainian route separately. That keeps the next check concrete and gives the team an honest account of what visitors can do today.

Use this checklist on your next release

First, verify the deployed revision and open the exact canonical URL a visitor will use. Follow it with a tracking parameter, too, if your campaigns add one.

Second, check the rendered page after scripts finish. Confirm that the headline, image and first action are what you shipped. Compare transferred bytes or field performance before calling a change faster.

Third, tap the primary action at a mobile width. A service page should lead to the intended form, an article to a useful next read and a product listing to a real inquiry path.

Finally, inspect the URL in Search Console. Record the live result and the index status separately. Today’s live page and Google’s last recorded copy can differ.

One useful release note has four pieces: the URL, the deployed revision, the action you tested and the thing you actually observed. Write those down before calling the page done.
